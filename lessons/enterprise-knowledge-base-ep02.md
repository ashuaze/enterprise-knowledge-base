# 02｜企业资料散在各处，怎样收集并接入知识库？

**企业级知识库设计与检索质量工程 · 第一阶段**  
阅读约 25–30 分钟 · 可选练习约 10 分钟 · 所有业务数据均为合成示例

Atlas 项目负责人想知道外包工程师第一天要办什么。行政同事发来一份扫描的入场规定。共享盘上还有一份名字很像的旧版，门禁办理人写在表格里，申请账号的入口则在 IT Wiki。有人建议先把一个目录里所有文件批量上传。过了一周，知识库里出现了三条同名规定，其中一条是草案，另一条来自权限更宽的项目备份目录。系统已经收到字节，但还无法回答哪一条是当前正式来源。

本期设计入库入口。读完可以划分**来源、文档、版本、原件和导入请求**，为重传、移动和新版本写出不同的处理规则，并说明连接器怎样从中断中恢复。

## 一、先决定收什么，以及谁能纠正它

从一个高价值问题倒推材料，比一次收全公司的网盘更容易验收。Atlas 入场至少需要办理条件、办理人、申请入口三个证据。它们可以来自三个维护团队。

| 材料 | 来源与责任人 | 权威范围 | 起步接入方式 |
| --- | --- | --- | --- |
| 行政入场规定 | 行政制度库，行政负责发布 | 各类外包人员入场条件和生效日期 | 上传扫描 PDF；人工确认版本和适用范围 |
| 门禁办理矩阵 | 共享盘受控目录，行政运营维护 | 区域与办理人对应关系 | 批量导入并校验文件与元数据清单 |
| IT 账号申请 Wiki | IT 空间，服务台维护 | 账号申请入口和操作步骤 | 连接器定期同步，保留源记录 ID |
| Atlas 联调手册 | 项目空间，项目负责人维护 | 项目成员可查看的联调说明 | 明确连接器范围和原始权限，再接入 |

资料盘点至少记录来源标识、维护人、可导入范围、权限来源和预期更新频率。一个来源可以对某个字段有权威性。例如行政负责入场条件，Wiki 可以解释怎么提交工单。两个地方出现相同文字时，仍然需要各自的来源记录。权限、审批和版本都可以沿各自的业务链变更。

先试点四份材料。对照问题逐项问清楚「缺哪个字段就不能办理」「旧版应否继续可查」「来源由谁确认」。第 01 期的现行与历史查询，会依赖这里登记的版本和业务生效时间。

## 二、原件、版本和导入请求有不同的标识

文件名可能改，保存位置可能变，字节相同的文件也可以有不同的读者。保留几个独立的标识，才能描述这些情况。

| 对象 | 关键字段 | 约束和用途 |
| --- | --- | --- |
| 来源 `Source` | `workspaceId`、`sourceId`、连接器类型、授权配置引用 | `sourceId` 指企业中的一个接入实例。两个 Wiki 空间可以属于同一供应商，仍各有一个接入实例。 |
| 源记录 `SourceRecord` | `workspaceId`、`sourceId`、`externalId`、`displayPath` | 前三个字段组成稳定身份。上游移动文件时更新展示路径；上游缺少稳定 ID 时需明确采用路径作为身份及移动后的合并流程。 |
| 源版本 `SourceRevision` | `recordId`、`revisionKey`、`rawAssetId` | 同一条记录下，版本键唯一。API 来源以文档系统提供的版本标识为优先。人工上传由服务端给一次提交分配稳定的版本键。 |
| 原件 `RawAsset` | 对象键、字节大小、服务器计算的 `sha256`、检测类型 | 校验和可比对原始内容和检查传输结果。原件键应绑定不可变的已校验字节。 |
| 导入请求 `IngestRequest` | `uploadSessionId` 或导入批次及行标识、提交人、实际结果 | 给重试归并同一次操作；上传发起、确认接收和文档发布是不同的事件。 |

同一个行政 PDF 在「部门制度库」和「项目备份」各出现一次，两份字节可能有相同的 SHA-256，但对应两条源记录，分别保存来源和读者范围。即使底层以后选择复用某个物理对象，也要在授权边界内做，文档记录、权限判断和审计仍各自独立。首版可以按来源保存原件，减少权限、销毁和存储复用之间的耦合。

还有一种常见情况。第 1 版内容 A，第 2 版改成 B，第 3 版有意改回 A。第 1 版和第 3 版字节相同，却有不同的发布时间和版本身份。保留两条版本记录，历史查询才能复原各时期的决定。

## 三、从文件上传成功到原件登记成功

客户端拿到上传进度 100% 之后，还要由服务端确认对象确实属于本次会话，读取对象属性并完成类型、大小和内容校验。教程中，原件先隔离到私有存储，进入受限的验证路径。通过校验后，再把不可变的原件引用登记到源版本并安排处理。对上传者显示「已接收」「待校验」「被拒绝」等状态，能避免上传完成就被误解为可查询。文件类型以允许列表和内容检查为依据，原始文件名仅保留作展示；解析组件使用独立资源限制。 [OWASP 文件上传指南](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

| 接口或事件 | 读写哪些信息 | 成功表示什么 |
| --- | --- | --- |
| `POST /upload-sessions` | 记录来源、提交者、文档身份与允许大小 | 已分配会话和目标位置 |
| 上传到受控目标 | 写入本次会话的待验证对象 | 传输成功，可以进入校验 |
| `POST /upload-sessions/{id}/complete` | 校验会话和对象绑定；读取经验证的原件大小、类型与指纹 | 同一次提交获得稳定的接收结果；后续状态可查 |
| `GET /imports/{id}` | 读取接入结果、原因、目标版本及处理任务 | 上传者可区分等待校验、已登记与需要修复 |

小文件可由应用服务接收和流式写入，便于校验链路集中管理。大文件可以使用受限、短时的直传能力，应用依然负责确认对象属于会话，以及读到的已校验对象版本与持久化引用一致。实际部署时，可用对象版本 ID 或不可变键固定已校验对象，防止确认后读取到另一份字节。

### 核心代码走读 · 同一源版本应该怎么处理

下面的 TypeScript 片段把身份判断和重传判断收在一个函数中。调用者已经验证上传和身份，并以 `workspaceId + sourceId + externalId + revisionKey` 查出已登记版本。函数返回应继续登记、复用已有版本还是报告冲突。

```ts
type VerifiedRevision = {
  workspaceId: string;
  sourceId: string;
  externalId: string;
  revisionKey: string;
  sha256: string;
};

type RecordedRevision = Pick<VerifiedRevision, "sha256"> & {
  versionId: string;
};

function decideRegistration(
  candidate: VerifiedRevision,
  existing: RecordedRevision | undefined,
):
  | { action: "register"; key: readonly [string, string, string, string] }
  | { action: "reuse"; versionId: string }
  | { action: "conflict"; reason: "revision_bytes_changed" } {
  if (existing === undefined) {
    return {
      action: "register",
      key: [candidate.workspaceId, candidate.sourceId,
        candidate.externalId, candidate.revisionKey],
    };
  }
  if (existing.sha256 === candidate.sha256) {
    return { action: "reuse", versionId: existing.versionId };
  }
  return { action: "conflict", reason: "revision_bytes_changed" };
}
```

行政同事上传成功后，应用收不到确认响应，于是用原会话重试。查询到同一个版本键，字节指纹一致，返回先前分配的版本 ID。若同一版本键下出现不同字节，记录冲突，由导入方确认是重复使用了会话还是上游修订标识异常。经过确认的新版本会有新版本键。

并发仍由持久层负责。两条请求可以同时读到「尚未登记」。生产实现应在版本表建立组合唯一约束，用冲突处理后再核对先前记录，确保两个请求得到同一个接收结果。版本与后续处理任务应处于同一个事务或由可靠事件补齐，第 05 期会把这个例子展开。 [PostgreSQL INSERT 与 ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html)

## 四、批量导入和连接器复用同一条登记规则

批量导入可以先生成一份**预演报告**。逐条列出会新增、会复用、发生冲突、待补权限或会拒绝的材料，以及数量和原因。确认后再处理符合条件的行。一个批次中有部分错误时，重传只需针对失败行操作，每一行可通过上面的导入请求标识对账。

| 同步方式 | 何时适用 | 执行策略 |
| --- | --- | --- |
| 全量枚举加差异比较 | 来源小、更新不频繁或接口不支持可靠增量 | 保存上次已确认的来源清单，按源记录和版本比对。只有完成一次授权范围明确的全量对账，才把未出现项视为待确认删除。 |
| 增量游标 | 来源明确提供变更标记和分页协议 | 每页持久化变更和处理任务后再保存继续标记。中途崩溃可以重放已确认之外的页面，版本登记自身必须幂等。 |
| 事件通知加周期对账 | 需要更快发现变更，并允许定期修复漏通知 | 通知用于触发同步，权威内容和权限仍由上游确认；根据上游顺序和本地版本状态处理重复与乱序。 |

把游标绑定到来源实例和查询范围，持久化的内容应能区分本轮分页的继续地址和整轮完成后的增量标记。上游明确宣告游标失效时，按接口语义启动新的同步轮次；先完成对账，再判断哪些记录真正缺失。授权失败和限流都有独立的状态与重试策略。连接器遇到无法读取的记录时，暂停暴露无法验证的内容并复核原因，具体撤权路径见第 10 期。 [Microsoft Graph 增量查询](https://learn.microsoft.com/en-us/graph/delta-query-overview)

## 五、如何验收这个入口

| 输入 | 预期结果 |
| --- | --- |
| 同一上传会话确认两次，指纹相同 | 同一源版本和同一接收结果 |
| 同一源版本键提交不同字节 | 阻止覆盖，记录版本冲突 |
| 源记录 ID 相同，文件改名或移动 | 更新展示信息，原有版本与引用仍可追踪 |
| 两个授权范围的文档字节相同 | 两条源记录，权限继续独立判断 |
| 解析前发现文件不符合接入约定 | 保留可审计的失败状态，由上传方修正 |
| 增量同步在写入变更后、保存游标前崩溃 | 重放该页不会重复登记，游标可继续推进 |

**可选练习。** 用虚构的行政 PDF 运行上面的函数。依次测试首次登记、同一会话重试和旧键下换字节，记录三次决定。再写一条测试模拟「同一字节来自两个权限目录」，检查组合键中的 `sourceId` 是否使两份来源仍可独立管理。

原件进入系统后，扫描文件里可能仍有一页只有图像，表格标题也可能被拆到上一页。第 03 期会设计逐页识别与清洗，先得到可以审阅的结构化内容。
